# FabPilot — Learning Log

2–4 bullets per step: what I learned, what surprised me, what I'd explain in an interview.

## Phase 0 — Setup

### 0.1 Repo skeleton
- `.env` (real values, gitignored) vs `.env.example` (committed contract: every var, format, safe defaults). Pattern `.env.*` + `!.env.example` ignores all variants except the template.
- A leaked key is fixed by **revoking** it, not by deleting the file — git history keeps every commit and bots scan GitHub within minutes.
- Fallback model lists should span **different providers** so one outage/rate-limit doesn't kill all options; order by capability for tool calling, verify with evals later (8.6).
- `.gitattributes` with `eol=lf` prevents Windows CRLF from breaking shell scripts and Docker builds.

### 0.2 Postgres + TimescaleDB + pgvector
- Extensions must be in the image **and** enabled per database with `CREATE EXTENSION`; pgvector's SQL name is `vector`. `<#>` returns the *negative* inner product so ASC ordering still ranks best-first.
- `/docker-entrypoint-initdb.d` scripts run only on an **empty volume** — recreating the container isn't enough, it needs `down -v`. Long-term schema changes belong in **migrations** (Alembic), which track what each DB has applied and work on production data.
- Tags are mutable, digests are immutable: pin third-party images by digest for reproducibility, and bump deliberately (Renovate/Dependabot) to still get security fixes. Own images: unique tags like the git SHA.
- Port clash with a native Postgres on 5432 → host port 5433. Verify image internals instead of assuming: this image's PGDATA is `/home/postgres/pgdata/data`, not `/var/lib/postgresql/data`.

### 0.3 FastAPI + /health + tooling
- **503 vs 500**: 500 = "I have a bug"; 503 = "I'm fine but can't serve right now (dependency down), try later/elsewhere". Load balancers / k8s readiness probes stop routing to a 503 instance *without restarting it* — restarting the API wouldn't fix a dead DB.
- **One engine per process** = one connection pool. An engine per request → no reuse + connection exhaustion (Postgres `max_connections`, one OS process per connection).
- Catch the right exception: `DBAPIError` covers driver/connection failures but not code bugs (those should still 500). Pool exhaustion raises SQLAlchemy's `TimeoutError`, which is *not* a `DBAPIError`.
- Windows gotcha: async psycopg can't use `ProactorEventLoop` (Windows default; uvicorn uses it unless `--reload`). Fix: `--loop asyncio:SelectorEventLoop` + pytest-asyncio's `pytest_asyncio_loop_factories` hook. Read installed library code instead of guessing.
- Config fails fast (`PostgresDsn`, required field); passwords in URLs must be URL-encoded; `POSTGRES_PASSWORD` only applies on first volume init.

### 0.4 GitHub Actions CI
- `uv sync --locked` fails if `uv.lock` disagrees with `pyproject.toml` → CI fails loudly on drift instead of silently resolving versions nobody else has (and that the Docker build won't have).
- Service containers give CI a real Postgres (same image digest as local). They start *before* checkout, so init SQL isn't mounted → schema/extensions must come from migrations.
- Local workarounds must not leak into CI: port 5433 was a laptop-only fix; on the runner it's 5432. Values written twice drift apart (password mismatch) — the health integration test caught it.
- Secrets: ask "what can someone do with this outside this run?". Throwaway CI DB password is fine in plain text; API keys go in GitHub Actions Secrets (`${{ secrets.X }}`, masked in logs, not exposed to fork PRs). Pin actions by commit SHA — tags are mutable.


## Phase 1 — Data & simulator

### 1.1 Models + Alembic migrations (quiz answers explained, not self-answered)
- Hypertables: every PK/unique key must include the time column (uniqueness is only enforceable per chunk). Composite index order: equality column first, range column last → `(sensor_id, time)` = one contiguous range scan.
- **Always review autogenerate**: it doesn't know TimescaleDB (hypertable is hand-written) and would have *dropped* Timescale's own `sensor_readings_time_idx` → `include_object` filter in env.py. Set the constraint naming convention before the first table (`column_0_N_name` for composites).
- `default=` is Python/ORM-only; `server_default=` lives in the DB and covers every writer (simulator bulk inserts, psql, other services). Invariants that must always hold go in the DB (`CHECK approval_recorded`).
- `alembic check` in CI catches "model changed, migration forgotten" (→ prod 500s on missing columns). Downgrades are for dev; in prod roll forward + expand/contract. Edit a migration only until it's pushed/applied elsewhere.
- Debugging a hang: `localhost` → `::1` first on Windows, async psycopg never notices the refused attempt → use `127.0.0.1` and give every network call a timeout. Tools: pg_stat_activity, faulthandler, minimal repro.

### 1.2 Seed script + plant.yaml
- Idempotency via upsert (`INSERT ... ON CONFLICT (cols) DO UPDATE`); the conflict target must match a unique constraint exactly. Select-then-insert is a TOCTOU race (concurrent seeds crash on the unique key, or duplicate without one) and an N+1 round-trip problem.
- One transaction for writes that only make sense together (atomicity): a failing statement aborts the whole transaction and `engine.begin()` rolls back everything — no half-applied state. Postgres never "skips the bad row".
- Config owns description, the running plant owns state: re-seed must not touch `status`. Only thresholds are re-seedable; `kind`/`unit` give meaning to stored history, so changing them = a new sensor.
- Validate config at the boundary (Pydantic `extra="forbid"`, ranges) before connecting. Read deprecation warnings: `Result.tuples()` is deprecated in SQLAlchemy 2.1 — check the installed version, not memory.

### 1.3a/b uv workspace + signal model
- uv workspace: one `uv.lock` + `.venv` at the root for api/simulator (+ later MCP/evals) → no version drift between packages. A member that others import must be a real package (build backend, `py.typed` per PEP 561 — without it mypy treats the import as `Any`; CI missed it because it type-checked both packages together).
- Healthy signals = schedule (OFF/IDLE/RUNNING, Berlin local time incl. DST) + job load + per-kind physics + first-order lag + noise, all from one seeded RNG (keyed by crc32(machine code), so adding a machine doesn't change the others). Warm-up after shift start leaves the normal band → anomaly detection must know the operating state.
- First-order lag: Euler `alpha = dt/tau` overshoots for alpha > 1 and diverges for alpha ≥ 2 (error × (1−alpha) per step); exact `alpha = 1 − exp(−dt/tau)` is always in (0,1). It's a recurrence (each output needs the previous) → not a plain numpy expression; it's a first-order IIR filter (`scipy.signal.lfilter`) = the EMA used in anomaly detection.
- Test the property, not one implementation's numbers: my exact-equality test broke when the implementation got more correct.

### 1.3c Writing readings (backfill + live)
- `COPY ... FROM STDIN (FORMAT BINARY)` for bulk loads: no per-statement overhead, no 65,535-parameter limit. Idempotent backfill = DELETE window + COPY in one transaction (COPY can't ON CONFLICT). 3M rows in ~35 s.
- Measure before optimizing: simulation (incl. the Python lag loop) took 0.8 s; 97 % of the time was 3M Python `write_row` calls. Left as is: one-off backfill, simpler code wins until it hurts.
- psycopg defaults to autocommit=False: the first SELECT opens a transaction and every `conn.transaction()` becomes a SAVEPOINT → nothing commits until close. Hidden in backfill (CLI closes the conn), fatal in the never-ending live loop. Fix: `autocommit=True`. Tests missed it because they read through the writer's own connection → regression test reads from a SECOND connection and uses the real `connect()`; verified it fails with the bug.
- Plan randomness in fixed blocks of absolute time so a 10 s live tick and a 7-day backfill see the same plant; windows are [start, end) so live resumes exactly at the backfill's end; `initial` carries lag state across the boundary.

### 1.4a/b Faults + alarms
- Physical faults change the process (target → through the lag: temperatures rise with tau); sensor drift changes only the measurement (after noise) → every other sensor stays bit-identical. That pattern — alarms from ONE sensor while physically linked sensors (load, pressure) stay normal — is how a human (and the agent) tells drift from a real fault. Real plants use redundant sensors + voting (2oo3) so one drifting sensor can't trip a machine.
- A signature that passes for one seed may be luck → checked each fault across 30 seeds.
- PLC alarms: debounce (N consecutive samples to RAISE) + hysteresis (a different, safer level to CLEAR) + state-aware (no low-pressure alarm while stopped/warming up). Without them: alarm floods (ISA-18.2). Debounce belongs to raising, hysteresis to clearing — resetting the counter at the clear level lets an oscillating sensor alarm. Low alarms = the same state machine on the negated series.
- Healthy data must be silent (a week, 10 machines, 0 alarms — enforced by a test), or real alarms drown in noise.
- Run commands from the directory their paths are relative to (mypy from the repo root); an unsaved editor buffer is not the file on disk.

### 1.4c Ground truth, inject, migration 0004
- Ground truth lives in a separate Postgres schema (`sim`) so the agent's DB role can be denied access with GRANTs — the answer key must be unreadable by the system being graded, enforced by the DB.
- Roll-forward on a published schema: 0004 only adds. A nullable column without default is a metadata-only change in Postgres (instant, no table rewrite) — the safe first step of expand/contract.
- `include_schemas=True` alone made autogenerate want to DROP TimescaleDB's catalog tables (`_timescaledb_catalog.hypertable`, ...) → allow-list of managed schemas via `include_name`. Allow-list > block-list: stays safe when an extension adds new internal schemas. Autogenerate also never emits `CREATE SCHEMA`.
- Atomic inject (ground truth + readings + alarms + status in one transaction), proven by a test that fails the alarm write halfway and asserts nothing landed. Exclusive window ends cut off the "now" sample → a fault fully developed now never tripped until the current grid point was included.
- Real alarm logs repeat: a standing condition re-alarms after every restart (67× VIB-HIGH). ISA-18.2 handles it with shelving; the agent must read "many alarms, one sensor, rising" as ONE developing problem.
- Quiz 1.4 (corrected): keep the answer key out of the agent's reach by ENFORCEMENT (separate schema + DB role without privileges), not convention — a generic `run_sql` tool or a prompt injection would otherwise leak it and make eval scores meaningless (data leakage). Least privilege / defense in depth.
- Quiz 1.4 (corrected): never rank causes by alarm COUNT (it measures restarts/chatter). Use distinct conditions (sensor+code), order of first appearance, escalation/trend, and cross-sensor patterns → tools must summarize alarm logs into conditions + timelines before the LLM sees them.

### 1.5 Read endpoints + time_bucket
- Aggregate in the DB: `time_bucket(interval, time)` + avg/min/max/count per bucket. avg alone hides spikes (a 10 s spike to 90 °C moves an hourly avg by 0.14 °C) → always return min/max for anomaly data. `count` exposes partial buckets and gaps.
- Protect the system: a fixed bucket ladder (enum → 422 before any SQL), auto-pick the smallest bucket that fits, hard cap of 500 points. Chunk exclusion: a time-range WHERE only touches the relevant hypertable chunks.
- Half-open ranges `[start, end)` tile perfectly: no duplicate at the boundary, no gap from "23:59:59" tricks (microsecond timestamps). Same convention as Python ranges, time_bucket and the simulator windows.
- Bind every value, even "safe" enum ones: correct typing (timedelta → interval), one query text → plan reuse / psycopg auto-prepare, grouped stats in pg_stat_statements, defense in depth. Raw SQL in text() isn't checked by mypy → integration tests catch typos like `FROM readings`.
- A SQLAlchemy Row is a tuple: `row.count` is `tuple.count()`, `row.t` is a legacy shortcut → read by name via `result.mappings()` or unpack.

## Phase 2 — LLM gateway

### 2.1a Gateway core (fallback, retries, budget)
- Error taxonomy decides everything: transient (timeout, connection, 5xx, short 429) → retry same model with backoff; "this model is out" (404, long Retry-After) → next model; our side / account-wide (400, 401, quota) → fail fast — retrying or falling back only burns quota and delays the error.
- Fail closed on unknown errors: a wrong RETRY silently burns budget and hides the bug; a wrong FAIL is one loud, visible error you then add to the taxonomy (same idea as deny-by-default and safety interlocks).
- Exponential backoff with jitter (avoid thundering herd); Retry-After wins but capped; a TOTAL attempt budget + wall-clock deadline per call (3 models × 3 retries would be 9 requests of a 50/day budget). One component owns retries: SDK retries off (2.1b) or they multiply.
- Inject sleep/clock/rng → retry scenarios that take minutes run in ms, deterministically. `Protocol` = structural typing: a fake provider fits without inheriting.

### 2.1b OpenRouter provider + first real call
- Docs ≠ reality: an unknown/removed model returns 400 "not a valid model ID" (docs: 404) → mapped to ModelUnavailable so a rotated-away free model falls back instead of failing every call. Per-minute and daily 429 are identical except `X-RateLimit-Reset` (hours away = account-wide daily quota → fail fast).
- Check the installed library, not memory: openai 3.x uses `httpx2`, so respx would have mocked nothing → inject `httpx2.MockTransport` (no extra dependency, explicit).
- Exactly one layer owns retries (`max_retries=0` on the SDK): otherwise 4 gateway attempts × 3 SDK requests = 12 per question, blind retries on the daily-quota 429, and wrong latency/deadline accounting (retry storms in production).
- HTTP 200 ≠ success: check for an embedded `error`, empty choices, and "no content + finish_reason=length". The first real call failed exactly so: a reasoning model spent 20/20 tokens thinking. → OutputTruncatedError (FAIL, our budget) + record finish_reason/reasoning_tokens (85 % of a real answer's tokens were invisible reasoning). Unchecked, the agent would read silence as "insufficient data" and the 2.3 cache would replay it forever.
- Secrets: SecretStr (masked in repr/logs); real-LLM tests behind a `llm` marker deselected by default, verified with --collect-only before spending quota.

### 2.2 Call log (llm_calls)
- One row per ATTEMPT, grouped by call_id: retries and fallbacks stay visible. Recorded in `finally`, so failed calls are logged too (the rows you most want later). UNIQUE(call_id, attempt_no) also serves call_id lookups → no redundant index.
- Observer pattern (CallRecorder Protocol): gateway reports, doesn't know about Postgres. Logging is best effort — a recorder failure is logged as ERROR and swallowed; the user still gets the answer. Seen for real: smoke.py hit the ProactorEventLoop bug, answer still returned, failure loud.
- Store a hash, never prompt text (logs end up in dashboards/exports). Canonical JSON: sort dict keys (JSON objects are unordered by spec), never lists (arrays are ordered = meaning), compact separators, ensure_ascii=False + explicit UTF-8. HASH_VERSION = cheap cache invalidation.
- Model left out of the hash so the 2.3 cache answers "same question" across fallbacks — but for model comparison (8.6) that would compare the cache with itself → cache off or keyed per model for evals.
- Same prompt, same hash, different answers/tokens/latency: LLMs aren't deterministic even at low temperature — caching trades freshness for reproducibility. A rule people must remember (loop_factory) belongs in ONE helper (app.runtime.run); tests on the selector loop couldn't catch the real entry point's bug.

### 2.3 Prompt cache (llm_cache)
- Cache in FRONT of the fallback loop: a hit costs no request (real: 1437 ms → 47 ms, 0 tokens) and is still logged in llm_calls (`cached=t`). Only clean answers are stored (finish=stop, non-empty), or a bad answer replays forever, instantly and unsuspected. A broken cache = a logged miss, never a failed call. Policy SHARED vs PER_MODEL: model comparisons must not share answers.
- `get()` is ONE `UPDATE … RETURNING` (fresh? + count + read can't race), inside `engine.begin()`: with `connect()` and no commit, SQLAlchemy 2.x rolls back on close → the caller gets the answer but the hit vanishes; only a test reading via a separate connection catches it.
- An upsert's conflict rule must cover every reason a row can already exist: `DO NOTHING` was right for a fresh duplicate (stampede: first answer wins) but an EXPIRED leftover then blocked every new put → that prompt missed forever. Fix: `DO UPDATE … WHERE created_at <= now() - ttl` (same freshness rule as get). Found from the quiz question "why not delete on the spot?"; regression test verified to fail on the old code.
- Order-dependent test failure = shared global state: Alembic's `fileConfig()` disables all existing loggers by default, so after an in-process migration the gateway's ERROR logs were silently gone → `disable_existing_loggers=False`. And: never run `ruff --fix` on a file with a TODO — it deleted the import the TODO needed.

### 2.4 Ollama provider — skipped (optional; free quota is enough for now, revisit for bulk evals in Phase 8)

### 2.5 /gateway/stats
- Know the grain: one llm_calls row = one ATTEMPT. requests (attempts that reached a provider) is what the quota counts — an upper bound, rejected 429s may not count; calls = distinct call_id; a call FAILED when no attempt succeeded (`bool_or(status='ok')` per call_id in a CTE). Cache hits are calls but not requests.
- Percentiles, not averages (nine 1 s + one 30 s = 3.9 s average, nobody's experience). `percentile_cont(...) WITHIN GROUP (ORDER BY latency_ms) FILTER (WHERE status='ok')` = how fast a model ANSWERS; always show it next to the error rate — success-only looks great when 90 % fail, all-attempts is skewed both ways (60 s timeouts up, instant 400s down). And p95 over n=3 is just interpolation: show the sample size.
- `FILTER (WHERE …)` = several conditional aggregates in one pass; aggregates without GROUP BY always return one row, but `sum()` over no rows is NULL → `coalesce`. A bounded window (`hours` 1–720) keeps the query on the time index.
- My wrong expectation (failed_calls ≥ 1) was a lesson too: the 2.1b failure happened before llm_calls existed — a log only knows what happened after it was built.

## Phase 3 — Knowledge base & RAG

### 3.1a Corpus format + 5 manuals
- The corpus is DESIGNED like test data: right answers, near-misses (bearing wear vs. misalignment, drift vs. overheating), out-of-scope causes as distractors, and no eval leakage (incidents dated before the simulated period; eval scenarios never copied from them).
- Strict frontmatter metadata (extra="forbid", doc_id format per type) = what retrieval filters on and citations point to: a typo'd key would be a document that silently never matches a filter. `yaml.safe_load` always — the corpus will not stay "files we wrote ourselves" forever.
- Docs as code: a test checks every manual's signal table against plant.yaml AND the simulator's alarm rules. It lives in simulator/tests because that's the only place that can import both sides (dependency direction); duplicating the rules in api would check docs against a copy that drifts too.
- Writing the pump manual exposed a simulator realism bug: a clogged strainer made the centrifugal pump draw MORE current (wrong: power ~ flow, so less). Fixed by passing machine_type into the fault effects (also removed a `normal_max < 5` hack that guessed the pump from a range); regression test verified to fail on the old sign. Domain knowledge finds bugs no unit test asked about.

### 3.1b Nine SOPs + reference check
- SOPs carry what a work order needs: parts with part numbers, duration, staff, numbered steps, ⚠ STOP hold points, acceptance criteria. Structure is enforced by a test (6 required sections) because 5.2 builds work orders from it and 5.5 can check that safety hold points survive.
- Every document ID cited in any body must exist (collect all broken refs, assert once → one red run shows everything; alternative: parametrize per document). Same idea as citation validity in 8.3.
- Tests check numbers and IDs, not whether FACTS agree: I had written that swarf in M-09's strainer comes from the CNC coolant filters, while the CNC docs say they have their own pumps. Only a human (or careful re-reading) catches cross-document contradictions — and the agent would have reasoned from the false link.
- Generic SOPs list all 5 machine types (schema forbids empty). Trade-off: a 6th machine type would need every generic doc edited, silently invisible if one is missed → a `scope: general` flag is more robust; decide when writing the filter in 3.3.

### 3.1c Thirty incident reports
- Incidents are evidence by analogy and the most leakage-prone documents: dated before the simulated period (test-enforced). Leakage here = RAG retrieves a report of the very event being evaluated, whose root cause is in its text → the eval measures copying, not diagnosis (train/test contamination).
- Labels are ground truth, so they're tested for consistency (sensor drift ⇔ false alarm) and balance (every FaultType ≥ 2, ≥ 4 causes the simulator can't produce, ≥ 4 false alarms). Near-misses teach distinctions: same `RPM-LOW`, opposite causes (jam: current up; slippage: current down); same high vibration, different time patterns (wear grows, soft foot is constant from the start, a crash steps up then grows).
- Realism review of my first draft of INC-2026-901 found what no test checks: a LOW alarm 34 min after start-up (impossible: evaluated only after the warm-up hour), "drift" happening within one morning, "recalibrated" instead of a cause, ranges instead of numbers. A false-alarm report's strongest line is a comparison (reference 4.4 bar vs. transmitter 2.8 bar) plus the physical argument (no coolant → spindle can't stay at 45 °C).
- Honest note: at my request Claude rewrote 901 and wrote 902, so the 3.1c TODO isn't mine. Compensation: I write the 20 retrieval-eval questions in 3.4.

### 3.2a Structure-aware chunking
- One chunk per ##/### section (our documents were designed with meaningful boundaries); only oversized sections are split further — at blocks, then list lines, then words, tables by rows with the header + separator repeated (a row without its header means nothing). No overlap: overlap is a workaround for ARBITRARY boundaries (fixed-size chunks), here it would only duplicate text in results.
- Context header on every chunk ("MAN-PMP-001 · title · §5.1 … (in 5. Troubleshooting)"): the embedding knows what the text is about, and the citation ref comes for free.
- Over the model's limit (512 tokens) the embedding silently truncates: the text is stored and shown to the LLM, but the vector never saw the end → that content is unfindable while the chunk looks complete. Hence the token counter is injected and the budget (350) is checked with the real tokenizer in 3.2b.
- Corpus-wide tests catch what unit tests can't: no chunk over budget, no content line lost, every numbered section citable. 44 docs → 341 chunks, mean ~97 tokens: small chunks are precise but low-context — whether to merge is a question for the 3.4 eval, not for intuition.

### Extra: pre-commit hooks
- A pre-commit hook runs before every `git commit` and blocks it on failure. `.git/hooks` isn't versioned, so the `pre-commit` tool keeps the config in the repo (`.pre-commit-config.yaml`) and `pre-commit install` wires it up per clone.
- Local hooks (`language: system` → `uv run ruff`) use exactly the locked ruff version CI uses and download nothing. Only fast checks belong in a hook (format, lint, secret scan); mypy/pytest stay in CI, or the hook gets skipped.
- The manual pre-commit secret checks became hooks (`language: fail` for `.env`, `pygrep` for key patterns) AND run in CI, because hooks can be skipped with `--no-verify` or never installed: CI is the gate, the hook is the fast feedback. Verified that each hook actually blocks (bad format, fake key, `.env`).

### 3.2b Embeddings + pgvector + idempotent ingestion
- fastembed (ONNX) instead of sentence-transformers: on Linux the default PyTorch wheel pulls 2-3 GB of CUDA libs into CI and Docker for a CPU-only model. Same bge-small weights (quantized "-onnx-Q" export), behind an `Embedder` protocol so the library can be swapped. Verified facts first: 384 dims, 512-token limit, query prefix optional (passages none), normalized vectors (cosine = dot).
- Silent truncation lives in the measuring tools too: the model's tokenizer AND fastembed's public token_count() cap at 512, so a 2 002-token text "counts" as 512. Our counter is a tokenizer copy with no_truncation(). Real tokens vs chars/4: tables up to 1.6x → chunk with the real counter (344 chunks, max 344 tokens).
- Idempotency = content hash (meta + body + chunker version + budget) AND model id (library version + exact source). Same text, new model → re-embed: vectors from two models live in different spaces, and mixing them fails silently (slightly worse scores, no error). Embed BEFORE the transaction (no row locks or pooled connection held during seconds of CPU; a failure writes nothing); replace each document in one transaction; delete documents whose file disappeared.
- Read generated code and library source, not memory: autogenerate emitted VECTOR without importing it; reflection needed `ischema_names["vector"]`; pgvector 0.5 returns list[float] (older versions numpy) — mypy was right and I first "fixed" the wrong side. TLS inspection: trust the OS store (truststore), never verify=False.
- First look at the vectors: neighbours of a false-alarm chunk are REAL bearing-wear incidents — embeddings capture topic, not the reasoning "vibration flat → sensor". Hence hybrid search + filters (3.3), reasoning over data (5.2), and measuring (3.4).

### 3.3 Hybrid retrieval
- Embeddings find meaning, full-text finds exact terms (PRESS-HIGH, suction_strainer_dp, SOP-GEN-004); hybrid runs both with the SAME filters applied inside each search (machine type via `:t = ANY(machine_types)`, document type). Generic SOPs survive a machine filter because they list all types.
- Checked the tokenizer before coding: codes survive ('press-low' + parts), but `websearch_to_tsquery` ANDs every word, so a natural question matches almost nothing → rewrite top-level & to | and let ts_rank_cd reward more matches. A STORED generated tsvector + GIN index: Postgres keeps it in sync, existing rows filled by the migration.
- RRF: sum of 1/(60+rank) — ranks, because cosine and ts_rank are on incomparable scales and not even stable across queries within one method. Cost: it ignores how much #1 beats #2.
- Real results beat my expectations: text puts the exact code row first; hybrid ranks the pump manual only #5 because RRF fuses per CHUNK and the manual's relevance is split over §4 and §5.1. Vector returned 5 chunks of ONE incident for a drift question, while text found SOP-GEN-004 — diversity matters (k is a budget; one source read five times = anchoring). Per-document cap / MMR: to be decided by measurement in 3.4, not by intuition.

### 3.4 Retrieval eval (20 gold questions, my own)
- Gold set with section-level references (§5 accepts §5.x, not §50), validated against the DB before running: a typo would silently count as a miss for every variant. Metrics: hit@5 (= recall@5 with one relevant item), doc-hit@5, MRR (how HIGH the hit is).
- Result: all variants 90-95 % hit@5 → ceiling; differences are ONE question (5 points) = noise. The signal is per category: vector 50 % on exact codes vs text 100 %; text misses a cross-machine question; hybrid best MRR (0.82). Prefix: no measurable effect (kept, per model card). cap2: identical everywhere (the 3.3 diversity case isn't in this set).
- Decision from evidence: hybrid is the default; max_per_doc stays optional. Known RRF weakness (Q04): an item #1 in only ONE list (manual §4 for TRIP) loses to items present in both lists (incident summaries) — agreement beats a strong single-list signal. Options later: weighted RRF, or the agent choosing text search for codes.
- Eval-design lessons: my first Q16/Q17 copied the decisive evidence almost verbatim from their incident reports. Rewritten to describe only the observation: still rank 1 — and the hit is real (the analogous incident, found via machine filter + topic), not the extra gold refs I had added. Whole-document gold refs make hits easier. Measure, but also audit what you measure.
- Metric limitation found: after the rewrite, 4 of 5 slots are the same incident and SOP-GEN-004 (the procedure) is missing — yet hit@5 counts a full hit, because it only asks for the FIRST relevant section. An agent needs several kinds of evidence (case + procedure + manual): Phase 8 needs a coverage metric, and that is where a per-document cap could finally show its value.

## Phase 4 — MCP servers

### 4.1a sensor-mcp: tools over a shared data layer
- One core, several adapters: queries + validation moved into app/plant_data.py (raises NotFoundError / InvalidQueryError); the REST router maps them to 404/422, the MCP server to ToolError. The 1.5 tests passed unchanged = proof the refactor kept behaviour. Neither adapter has logic of its own, so they can't drift apart.
- MCP: a typed function + docstring = a tool (JSON Schema from type hints and Field descriptions; ctx is injected, not an argument). Tool results are LLM context → aggregated readings, capped alarm lists. ToolError = an actionable message the model can fix; any other exception = generic error, details only in the server log (the model can't fix internals, and their text may leak them). Good messages say "got X, allowed Y, try Z", derived from the constants, never hard-coded.
- Verify the SDK, not memory: mcp 2.x renamed FastMCP → MCPServer; server.run() uses anyio's default loop (Proactor on Windows → async psycopg breaks) → run via app.runtime.run. In stdio mode stdout IS the protocol: one print() kills the connection (logs → stderr; a real-subprocess test guards it). anyio cancel scopes must exit in the task that entered them → no long-lived client in a pytest fixture.
- Ground-truth wall: no code path in plant_data or sensor_mcp may read the `sim` schema (test-enforced now, DB role in Phase 10). Tooling: pin versions for npx too (the unversioned `npx @modelcontextprotocol/inspector` resolved to the deprecated v1).

### 4.1b detect_anomalies
- Compute what can be computed, let the model judge: deterministic detectors turn ~10 000 minutes per sensor into a few findings ("vibration +140 % of band, rising"), and report the QUIET sensors too — for a false alarm, "the neighbours didn't move" is the evidence. Facts, not diagnoses: `isolated` (only this sensor changed) fits a drifting sensor AND early bearing wear (vibration first); the agent decides with the manual.
- Robust statistics: rolling median/MAD (×1.4826 ≈ σ) instead of mean/std, because a spike inflates its own window's std and hides itself; a min_scale floor for MAD = 0. State inferred from the current sensor (99.7-100 % agreement, measured) — 24/7 machines never stop, so "moves when stopped" can't apply to them.
- The detector was wrong four times on a HEALTHY week, each time for a nameable reason: statistically significant ≠ practically relevant (effect size), level change ≠ spike (compare before AND after), ramps add up (consecutive minutes), weekends change utility demand (trend threshold from the measured healthy maximum), and current + speed together = load change (rule from our own manuals). A filter coupled to another detector's threshold broke when that threshold moved → measure from the data. Every threshold is measured and commented with its evidence.
- A healthy-must-be-quiet test is the most important one: a detector that always fires trains the agent to ignore it. Final check on real dev data without ground truth: M-08 drift found as an isolated trend with 4 quiet neighbours, M-01 bearing wear as vibration +140 % / temperature +49 %, control M-05 quiet.

### 4.2 docs-mcp
- Search is ranked, reading is structural: search_docs FINDS the most similar chunks (an SOP's steps 5-9 may rank lower and silently go missing); get_document READS a section with its subsections, deterministically. The agent pattern: search -> cite -> read the cited section (procedures, full tables).
- Facts as fields: get_incident_report returns machine / fault / false_alarm / root_cause from the validated frontmatter, so the model never has to extract (and possibly mis-extract) them from prose, and later tools can filter on them. The narrative stays per section.
- Shared rules live once: the §5-contains-§5.1 rule (section_in) is used by the reader AND the 3.4 eval; domain errors moved to app/errors.py, re-exported explicitly (`X as X`) so no caller had to change. Expensive resources (engine + embedding model, ~5 s) load once in the server lifespan; tests inject a throwaway DB and the FakeEmbedder; one live test runs the real process with the real model.

### 4.3 Reality check: a strong model on our tools
- Pre-registration: expected tools, conclusions and red flags were written BEFORE the runs, so the judging couldn't drift towards whatever the model did (the anti-HARKing rule from research).
- Blindness is harder than it sounds: Claude Code in the repo root has file/shell tools (it Grep'ed `data/docs/` in Run 2 and could have read the `sim` answer key), and one conversation for all questions leaks earlier answers. Only a client with nothing but the MCP tools (Claude Desktop) measures the tools.
- A strong model HIDES tool weaknesses: in Run 2 it compensated with extra calls and Grep (answers 16/16); in Run 3 without that help it fell into the gaps (13/16): defaults past the data end, a silently truncated alarm list reported as the onset, "healthy right now" over zero data. The worst failure mode: a correct conclusion carrying a false fact.
- Self-grading is not grading: the model scored its own Run 3 answers 15/16; checking the claims against the DB gave 13/16. Every finding was verified before becoming a 4.4 task — three of the first twelve were partly wrong (hysteresis exists but is narrower than the noise; onsets 24 min apart, not the same minute; `fault` omitted consistently, not null).
- Main lesson for 4.4: incompleteness must be IN the result (data_ends_at per machine, truncated + total_count, why minutes are missing, checks that weren't possible), because "nothing found" is ambiguous and a model fills the gap with a story.

### 4.4a Completeness in tool results (sensor-mcp)
- A tool result is an API contract: what isn't in it doesn't exist for the model, and it fills the gap with a story. "Nothing found" has three meanings (nothing happened / machine off / no data), so results now say which: per-machine `data_ends_at` + a `coverage_note` sentence, `last_reading_at` next to `status`, `minutes_running/stopped/no_data`, `checks_not_possible` ("no finding here is NOT evidence"). A sentence from the tool is the same truth for every client — no model has to subtract timestamps itself.
- Truncation must be visible: newest-first + limit silently drops the OLDEST rows, i.e. the onset — exactly what a root-cause analysis needs (Run 3 reported the cut-off as the onset). → `total_count` + `truncated`; changing list → object is a breaking change (fine with only our tests as consumers; external clients would need versioning or a new tool).
- Constraints belong in the schema (`ge=1, le=200` → minimum/maximum the client sees before calling), not only in error messages; durations must be exact (timedelta.days rounded 7 d 14 min down to "7 days"). Half-open windows apply everywhere: data starting AT `end` is outside.
- Measure before blaming: a 3× slower suite was not the new LATERAL index probes (4.9 ms on 3 M rows) but per-test DB setup and machine load. "All green" means tests AND ruff AND mypy: a lambda passed the tests but failed lint (E731) and strict mypy (untyped call).

### 4.4b list_incident_reports + descriptions that switch tools
- Two kinds of question need two tools: search answers "what do we know about this?" (ranked by similarity; k slots shared by several chunks of the same report, so k=10 may be only 4-5 reports), a list answers "which / how many?" (complete, from the validated frontmatter). Protocol Q5 is now a test: M-09 = 6 reports, exactly 1 false alarm, in one call.
- JSONB querying: `meta->>'machine'` (value as text), `meta ? 'fault'` (key exists), `(meta->'false_alarm')::boolean`. `NOT (meta ? 'fault')` states the convention "no simulated fault = key absent"; `meta->>'fault' IS NULL` would also match an explicit JSON null that might one day mean "not classified yet". At scale: a GIN index on `meta`.
- Descriptions are behaviour: search_docs now says when to switch ("one hit = one chunk → get_document before recommending a procedure"; "which / how many → list_incident_reports"), and `fault` is an enum in the schema (`$defs` + `const: "none"`) so the model sees valid values before calling.
- mypy narrowing: `==` doesn't narrow `FaultType | Literal["none"]` (a StrEnum member IS a str), `isinstance` does; use the public `.value`, never the internal `_value_`.

### 4.4c Fixes from Run 4, and Phase 4 in one paragraph
- The before/after run (Run 3 → Run 4, same client, only the tools changed) moved tool use 12 → 14/16; answers stayed 13/16, but the CAUSES of the false facts changed: no more silent gaps, instead two new tool problems — both mine. F17: the detector's 60-min warm-up also delayed the HIGH side (the PLC only waits for LOW), which shifted a finding 24 min and became a false "same minute" claim. F18: coverage_note measured the gap to the WINDOW end, and a model read it as the age of the data. Fixed both, plus F19 (one concept, two spellings: `fault: null` vs `fault="none"`). These fixes were done at my request (no TODO of mine in 4.4c).
- A test must fail on the bug it targets: the first F17 test compared against the first PLC alarm and failed for an unrelated reason (single noise peaks vs the 10-consecutive-minute rule). The replacement is a synthetic series, checked to fail on the old rule.
- Phase 4 lesson: a strong model hides tool weaknesses by compensating; evaluate without help, pre-register expectations, verify every claim (self-grading said 15/16, the DB said 13/16), and put completeness INTO the results. Open: F4, F7, and a truly blind Desktop run.

## Phase 5 — Incident agent (LangGraph)

### 5.1 Concepts and our graph (docs/agent-design.md)
- Workflow, not a free agent loop: free models are unreliable, the budget is ~50 requests/day, and the first investigation steps are always the same. Code runs the fixed tool calls, the model judges; one bounded follow-up loop (max 2) where the path can't be known in advance. A free loop fits open-ended tasks with unpredictable tool choice and a strong model.
- LangGraph: typed state (each node writes only its fields), nodes (LLM or code), conditional edges carrying the stop conditions, a Postgres checkpointer (state saved after every node per thread_id), interrupt() + Command(resume=...) for human approval.
- On resume the interrupted node re-runs from its start: anything before interrupt() runs twice — an LLM call there would cost a second request AND could produce a different work order than the one approved. So await_approval contains only interrupt(); the only DB write comes after it.
- Code decides what isn't judgement (machine regex, window anchored to data_ends_at, data age, citation validity); agent LLM calls go through our own gateway (fallback, cache, cost log), a deliberate deviation from ChatOpenAI to discuss in 5.2. Process note: I summarised the graph after reading the design (not an independent sketch); my summary missed the two edge paths: a valid run can end WITHOUT a work order (healthy machine → report), and stale/missing data goes to report_insufficient already at assess, before any LLM call.

### 5.2a Agent foundations: structured output, tools, triage, investigate, routing
- Check before installing: langchain-mcp-adapters 0.3.2 pins mcp<2; in our ONE workspace venv it would have downgraded the servers' SDK (MCPServer is 2.x only). The agent uses mcp.Client directly — and starts the servers as stdio SUBPROCESSES, because importing them from `api` would be a dependency cycle. langgraph 1.2.22 added only new packages (verified: nothing downgraded); langsmith comes along but sends nothing unless LANGSMITH_TRACING is set.
- Structured output without ChatOpenAI: schema in the prompt, JSON extraction (fences, prose), pydantic validation, ONE repair round that names the error, counted for the budget — through our gateway, so fallback, call log and cache still apply. A small protocol (anything with chat() → .text) lets the real gateway and a scripted fake both fit; the fake fails loudly on unexpected calls, which proves a path makes NO request.
- If a mistake is cheap, use a rule: triage needs no LLM request when the question has a machine code (6 of 8 protocol questions); a made-up code from the LLM fallback is discarded. investigate anchors the window to the data end (F2) and turns tool failures into evidence: "the world has no data" is a finding for the engineer, "our code crashed" is a bug — keep them apart.
- Routing in code (my TODO): stale data is a CONTEXT problem (diagnose the past, say the age), no readings is an EVIDENCE problem (anything said would be invented) → only the latter goes to "insufficient".

The model catalogue (/models, no quota) showed gemma doesn't reason by default.

### 5.3a Human-in-the-loop: pause, decide, save
- `interrupt(payload)` stops the run and stores the state in the checkpointer; `Command(resume=decision)` continues it. The trap: the interrupted node is re-run FROM ITS START, and the second time `interrupt()` returns the decision. So `await_approval` only asks and checks (pure, safe to repeat); the DB write is its own node, so the decision is checkpointed BEFORE the side effect and a failed save is retried without asking the human again.
- Route functions can only READ the state: error messages for the next question must be written by a node, so the check runs inside `await_approval`, right after the interrupt. The human's decision is untrusted input: a malformed payload re-asks instead of crashing a paused run, and an edit goes through the same `check_work_order` as the model's draft (a human can delete a lockout step too). That loop is bounded by the human and costs no LLM requests.
- The audit trail is in the schema: the DB refuses "approved" without who/when and "rejected" without who/why; the work order stores the exact draft that was signed (JSONB), incident + work order in ONE transaction. `resume()` refuses a run that isn't paused, so a second click can't save twice.
- At-least-once (my quiz answer): if the save commits and the process dies before the checkpoint, the save node runs again → a duplicate. Fix in 5.4: idempotency key (`UNIQUE thread_id` on work_orders + `ON CONFLICT`). Code hygiene: IDE auto-import pulled in `pyexpat.errors` for a local variable named `errors`; `assert` narrows types for invariants (our bugs), messages are for input errors.

### 5.3b Approval in the CLI + live run (approved work order saved, empty name sent back first)
- `input()` blocks the whole event loop; `asyncio.to_thread(input, ...)` blocks only its thread. The decision parser takes an injected async `read`, so it's tested with scripted keystrokes (like ScriptedChat). It does NOT validate names/reasons: check_approval does, and the live run proved it — the empty name came back as "! the decision needs the reviewer's name (by)".
- Checkpoint deserialization is a security boundary: restoring arbitrary types from a store lets whoever can write it choose what gets instantiated. LangGraph warns now and will block later; we pass an explicit allowlist (CHECKPOINT_TYPES). Test it by round-tripping every state field (warnings are logged once per process); a mutation check (drop `Approval`) proved the test fails — the object came back as a dict.
- A Postgres sequence never gives numbers back, even on rollback: work order #2 with no #1 is normal. Never count rows by id.
- My wrong prediction: the prompt cache gave 0 hits because the prompt contains the data age ("1 d 7 h 14 min ago"), which changes every minute. Caching needs a STABLE prompt: give the model a stable fact (timestamp + "stale"), let code write the exact age into the report (open item, before Phase 8 evals).

### 5.4a Postgres checkpointer: a paused run survives its process (live: paused, quit, --resume in a new process, saved #3)
- Same interface, different saver: `AsyncPostgresSaver` stores every step under the thread_id; the graph code didn't change. Resuming needs no MCP servers and no LLM (only await_approval + save_work_order run): a test resumes with `NoTools` and a model that may not answer.
- Two tools, one database, clear ownership: the library creates and migrates its own tables (`setup()`, own `checkpoint_migrations`); Alembic ignores them via `include_object`. Mutation check: without the filter, `alembic check` wanted to DROP them.
- Idempotent save in two layers: look first (my TODO: the normal path, inside the same transaction) + UNIQUE(thread_id) for the race (IntegrityError → return the winner's id; any other violation re-raises). Layer 2 alone is CORRECT but noisy: every repeat is a failed INSERT, a rollback and a burned id — so the test checks that the next run gets the next id. UNIQUE on a nullable column allows many NULLs in Postgres.
- The allowlist test had a hole: it round-tripped the state's FIELDS, but LangGraph also stores the graph INPUT (a whole AgentState) as a checkpoint write; `--pending` hit it. Now the whole object is round-tripped too, and a mutation check proves it. The run-specific `thread_id` comes from the node's `config`, not the state.

### 5.4b Run budget + step limit (live: 3 calls, 3 provider requests, 9,110 tokens)
- Calls ≠ requests ≠ tokens: one gateway call can be up to LLM_MAX_ATTEMPTS provider requests (fallbacks, retries), and the free tier counts REQUESTS. A meter (`Spend`) passed into chat_structured is updated after EVERY gateway call — also when it fails or the repair round fails — so nodes bill what a call really cost; failed calls now carry their attempts. Found on the way: a failed triage call wasn't counted at all, and a 4-attempt failure counted as "1 request".
- Check BEFORE the call, with a reservation (my TODO): allowed only if the remaining requests cover one call's worst case (`remaining < per_call` → refuse; `==` is fine). "At least 1 left" could end at 15 of 12; the reservation makes the budget a hard bound. A refusal is state, and the report says "budget used up", not "the model failed" — we stopped on purpose.
- The counters live in AgentState (checkpointed, reportable), not in a wrapper object. `RunBudget` refuses a config where not even one call fits (fail at startup, not on every question).
- `recursion_limit` counts STEPS, not cost: 20 = headroom over the longest correct path (11) so a legitimate new node doesn't break production, small enough to cut a routing loop quickly. Not enough alone: one step can make several calls of up to 4 requests each — hence both limits.

### 5.5a Work-order guardrails: map hold points, warn on missing steps, safety notes by code
- Map, don't count: "1 ⚠ STOP, 1 safety action" passed a draft that marked a harmless step as safety and dropped the real hold point. Now every hold point needs a safety action that references ITS location (my TODO, `check_procedure`). Parsing the real corpus first paid off: hold points sit on a step, on a continuation line (SOP-PMP-006) and on a whole section (SOP-GEN-001 §4.3); a test over all 9 SOPs fails if a new ⚠ STOP is missed.
- Strict vs. warn, decided per rule: reject only where a wrong result is worse than none (a missed lockout looks complete and can hurt someone); a missing ordinary step is a WARNING shown to the reviewer — free models condense steps, and rejecting would cost retries and often the whole draft. The human-in-the-loop is where warnings go.
- Policy by code, defence in depth: the SOP's §2 safety notes are attached verbatim; `safety_notes`/`reviewer_warnings` are hidden from the model's schema (`SkipJsonSchema`: what is ASKED) AND overwritten after validation (what is ACCEPTED) — otherwise the model could grade its own draft. The SOP the order follows is listed under Sources.
- Quiz insight, built in: a section hold point (§4.3 = steps 8-10) covered by ONE safety step was too weak — now ALL its steps need safety actions (ranges like "steps 8–10" or the bare section count). One helper (`Procedure.referenced`) serves both rules, and explicit steps win: "§4.3 step 9" is step 9 only, otherwise counting the section would hide that 8 and 10 are missing. Tooling lesson: ruff RUF001 flags a literal en dash; shell + Python + tool escaping mangled it three times — build the backslash with chr(92) when in doubt.

### 6.1a Agent service: runs as tasks, step events, run log
- The stream is a view, not the run: each investigation is its own asyncio task that writes RunEvents into a queue; a reader only drains it. A closed browser tab stops the reading, not the run (tested: nobody reads, the run still finishes, its state is in the checkpointer).
- Fail before streaming: once an SSE response has started, no HTTP error status can be sent. So `start()` raises Busy (429) / NotFoundError (404) BEFORE anything runs; everything after that is an event ("error", then "done"). The service has no FastAPI imports: plain RunEvents, the router makes SSE — testable without HTTP.
- At most 2 runs at once (free tier ~20 req/min). Check and increment with no `await` in between are atomic only because asyncio switches tasks at awaits; threads would need a lock, several pods a central limit (Postgres/Redis). Refuse (429), don't queue: a queue hides that nothing is happening.
- step_event (my TODO) is an API contract: what a watcher needs (counts, category, title, warnings), never what must stay on the server (SOP text, raw evidence); tested with REAL node outputs and a size/leak check. Open for Phase 10: orphaned runs after a restart (CancelledError skips `except Exception`; the row may stay "running") — find them on startup, mark them or resume from the last checkpoint.

### 6.1b HTTP routes with SSE (live: 8 events over curl, paused with the draft)
- FastAPI 0.162 has SSE built in (`fastapi.sse`: EventSourceResponse, ServerSentEvent, automatic `: ping` every 15 s) — no extra library. A path operation that yields events commits to "200 text/event-stream" with its first byte, so the run is started in a DEPENDENCY (my TODO): Busy -> 429 + Retry-After, unknown incident -> 404, both before any stream. Tested: a 404 arrives as application/json, not as an event stream.

- The browser's EventSource can only GET; our investigate is a POST. For Phase 7: POST to start, GET /runs/{id}/events to stream (native reconnect with Last-Event-ID; needs an event buffer per run) — the event ids exist already for that.
- Lifespan with AsyncExitStack: engine, checkpointer POOL (concurrent runs), gateway, service; closed in reverse order; the API starts even when the DB is down (/health says so). ### 6.2 Decisions over HTTP, work orders (live: approved -> #5 -> done, no LLM request)
- Status codes are a contract for the frontend: 404 no such run; 409 the request is fine but the resource's STATE isn't (already decided -> refresh and show who; still running -> keep listening); 422 well-formed but not acceptable (pydantic, or check_approval sent it back: the run stays paused, keep the user's input). The decision endpoint answers at once: only two quick nodes run, no tools, no LLM.
- "CRUD" cut down on purpose: create ONLY through a decision (a POST /work-orders would be a back door past the human-in-the-loop), update only allowed status transitions (my TODO: an allow-list, approved -> done, everything else refused — fail closed for statuses added later), delete never (audit). Known gap: `by` comes from the body until there is real authentication.
- Two locks, both mutation-checked: a per-run asyncio.Lock (without it, two simultaneous decisions both got 200) and SELECT ... FOR UPDATE for "done" (without it, the second click overwrites the first one's name). My first race test passed WITHOUT the row lock — the requests ran one after the other. A concurrency test must control the interleaving (transaction A holds the lock uncommitted, assert B is waiting, then commit) and must go red without the protection.
- Alembic autogenerate does NOT detect CHECK constraints: the new completion_recorded rule was missing from the generated migration while the model claimed it — added by hand; always read generated migrations.

### 6.3 OpenAPI as the contract (Phase 6 done)
- OpenAPI (with a P) is a spec format for REST APIs that FastAPI generates from the pydantic models — nothing to do with OpenAI, no LLM, no cost. Committed as api/openapi.json (deterministic: sorted keys, LF), it's the contract the frontend's TypeScript types are generated from (openapi-typescript): renaming a field in Python becomes a compile error (TS2353, proven in a scratch build), and the frontend builds without a running backend.
- The contract test (my TODO, `drift`): the committed spec must equal the app's; a red test says WHAT changed ("schema changed: DecisionOut") and HOW to fix it. My extra: filter path keys to real HTTP methods (a path item may also hold `parameters`, `summary`, ...).
- Writing the contract exposed real bugs: my explicit 422 had replaced FastAPI's validation-error schema (now anyOf sent-back | malformed); three 404s weren't documented; FastAPI documented the SSE route's JSON errors as text/event-stream. Readable operationIds (decide, listWorkOrders) become the client's method names.
- SSE payloads aren't enforced by anything (response_model validates JSON responses, not stream data): published as schema components, and a test validates every event of a real run against them. Safety: my mutation test would have reset uncommitted work with `git checkout` — blocked, rightly; mutations only with backup copies.

### 10.1a Production Dockerfile (one Python image)
- One image, several roles: the API starts both MCP servers as stdio SUBPROCESSES, so they can't be separate containers without moving to streamable HTTP; migrate / seed / ingest / simulator are just other commands of the same image. Multi-stage: the builder has uv and the caches, the runtime gets only /app and the model — uv never ships.
- Layer order is the build speed: manifests + uv.lock first (`uv sync --no-install-workspace`), then the model, then our code. Measured: a code edit re-runs only the COPY steps and the final sync. My first version downloaded the model AFTER the code (it imported our embeddings module), so every edit fetched 130 MB again — found by the quiz question, fixed by calling fastembed directly next to the dependencies, with the model name as ONE build arg shared with the app.

- Secrets stay out of the build CONTEXT: an allowlist .dockerignore fails closed; deleting a file in a later layer doesn't help, every layer stays in the image. And the install stays editable on purpose: config.py finds data/ from its own path, which site-packages would break. A container's `localhost` is the container: reach the host's DB via host.docker.internal (compose will give the DB a service name in 10.2).

### 10.1b Multi-arch build + what a release ships
- The Oracle VM is arm64, laptops and runners amd64: an image for the wrong CPU dies with `exec format error`. One tag, two images: buildx publishes a manifest list and each machine pulls its own. arm64 builds here under QEMU (~4 min cold); every native wheel we need (onnxruntime, psycopg-binary, numpy, tokenizers) exists for arm64 — checked in the arm64 image, not assumed. The classic `docker` driver refuses multi-platform builds outright; a `docker-container` builder (what setup-buildx-action creates in CI) does it, and a local image store holds one platform per tag, so arm64 is tested alone with `--load`.
- Size: 580 MB = ~120 base + 392 venv (onnxruntime 77, numpy 68, .pyc everywhere) + 65 model. My call: stay on Debian slim. pillow/hf_xet come only through fastembed (`uv tree --invert`), .pyc saves every cold start, alpine has no musl wheels for numpy/onnxruntime. Size isn't the bottleneck; what each RELEASE transfers is.
- That was the real win: one `COPY /app` shipped 394 MB per one-line fix. Splitting the COPY wasn't enough — the venv layer still got a new digest, because the builder re-ran `uv sync` after the code and rewrote files with new timestamps: a layer digest hashes the tarball, metadata included, so same content ≠ same layer. Fix: venv + model from a `deps` stage that never sees the code, code straight from the context, and only the 42 files our install adds (found with a diff of the file lists) from `builder`. Measured: ~0.6 MB per code release.
- Process lesson: measure the layers (`docker image inspect … RootFS.Layers` before/after an edit) instead of trusting the Dockerfile's intent — the split looked right and wasn't.

- Migrations are a one-off job, never in the API's startup: two replicas would migrate at once. And during a rolling update OLD pods run against the NEW schema, so migrations must be backward-compatible (expand/contract).
- Measured RAM, for sizing the VM and the pod limits: API at rest ~130 MB, Postgres ~55 MB, but the embedding model costs ~230 MB in the docs MCP subprocess that every investigation starts → ~0.55 GB per run, ~1.2 GB at 2 concurrent runs. A 1 GB VM is out; the API pod's memory limit has to be ~1.5 GiB (10.4), or the second run dies as OOM with no traceback. Later option: one long-lived docs server that loads the model once.

### 10.3 Kubernetes basics
- Declarative: I describe the desired state (2 replicas of image X, ≤ 1.5 GiB each), controllers compare it with reality in a loop and fix the difference. Pods are disposable — replaced, never repaired, new IP each time — so everything talks to a Service (stable DNS name), never to a pod.
- Mapped onto our compose stack: api → Deployment + Service; migrate → Job (Helm hook before the rollout); seed → a Job run by hand; simulator → Deployment, 1 replica; db → StatefulSet + PVC (k3s local-path); .env → ConfigMap + Secret (base64, NOT encrypted: protected by RBAC and by never being in git); ports → Ingress (Traefik in k3s) + cert-manager for TLS.
- Probes, the interview trap: readiness failing = out of the Service, keeps running; liveness failing = restarted. Our /health checks the DB, so it's READINESS; as liveness, a 2-min DB outage becomes a restart storm that fixes nothing (and recovers slower: 30 s startup each). All pods NotReady → no endpoints → a clear 503, the honest answer. Liveness needs a cheap "process alive" endpoint, which we don't have yet (10.4). Startup probe so liveness doesn't kill a pod still in its 30 s startup.
- A pod vanishing without a traceback: OOMKilled, exit 137 = 128 + SIGKILL, from the kernel (`kubectl describe pod`). Measured, not guessed: requests ~512Mi, limit ~1.5Gi — and the limit and AGENT_MAX_CONCURRENT_RUNS belong together, each concurrent run starts its own ~330 MB docs subprocess.

### 10.4a /livez, liveness without dependencies
- Two endpoints, two questions: /health = "can I serve?" (checks the DB → readiness: out of the Service, not restarted), /livez = "does the process still answer?" (touches nothing → liveness: restarted). Verified on the compose stack: DB stopped → /health 503, /livez still alive.
- /livez isn't useless for always returning 200: it fails exactly when the event loop is blocked (`time.sleep(60)` in an `async def` stalls EVERY request of that worker, /livez included) — the one failure a restart fixes. ruff's ASYNC rules catch that statically; liveness is the runtime net for what lint can't see. And a restart treats the symptom: a recurring block shows up as CrashLoopBackOff / restart count, an alert for Phase 9.
- Kept out of the OpenAPI contract (`include_in_schema=False`): an infrastructure endpoint for the kubelet must not change openapi.json and the frontend's generated types. A test pins that.
- The "Empty reply" right after `up` was the 30 s startup again — the window the startup probe will cover, so liveness can't kill a pod that is still starting.

### 10.4b Helm chart skeleton (Helm 4.3.2)
- A chart = Chart.yaml + values.yaml + templates. Values only for what differs between environments. Selector labels are separate from the other labels: a Deployment's selector is immutable after the first install, so nothing that changes (a version) may go in it.
- Secrets stay out of the chart: only `existingSecret` (a name). DATABASE_URL is assembled by KUBERNETES from `$(POSTGRES_PASSWORD)`, so the password is in no template, no value, no release history — and not in the Deployment, which far more people and tools may read (`get deployments`) than Secrets (RBAC separation).
- `checksum/config` on the pod template: env vars are read once, at process start, so a changed ConfigMap alone changes nothing in running pods; a changed checksum makes it a rolling update.
- My probes: startup → /livez (5 s × 8 = 40 s; /health here would turn a down DB at start into a restart loop), readiness → /health with timeoutSeconds 5 > DB_CONNECT_TIMEOUT 3 (a clean 503, not a probe timeout), liveness → /livez (10 s × 3). The bug: my startupProbe sat at POD level (6 spaces), valid YAML, so `helm lint` passed — lint checks syntax, not Kubernetes semantics; parsing the rendered output showed it. The 40 s budget is tight (30 s pool + imports): measure in 10.4d.
- readOnlyRootFilesystem tested BEFORE Kubernetes with `docker run --read-only --tmpfs /tmp`: model, both MCP subprocesses and uvicorn work. And the API refuses to start without LLM_FALLBACKS (fail fast) — which in a cluster is a CrashLoopBackOff, so the chart sets a default.

### 10.4c-1 Migrations in Kubernetes: initContainer + advisory lock
- The planned pre-install hook was a deadlock: Helm runs pre-install hooks BEFORE the chart's normal resources, so on the first install the migration waits for a DB StatefulSet that only gets created after the hook. post-install flips it: the API starts against an unmigrated DB (and /health's SELECT 1 would even call it ready).
- Instead: `alembic upgrade head` as an initContainer of every pod that needs the schema. Several run at once on a fresh install, and Alembic has no cross-process lock — test first: 3 processes, red with the predicted race ("alembic_version already exists"), green after my lock.
- My TODO: `pg_advisory_xact_lock(0x46414250494C4F54)` ("FABPILOT" in ASCII) inside the migration transaction, before run_migrations(): released at COMMIT or ROLLBACK, so a killed run leaves no lock; Alembic reads the version only after the wait, so the second pod finds head. Caveat for later: an autocommit_block() would commit mid-run and drop the lock early.
- A failed migration in a rolling update: the new pod sits in Init:CrashLoopBackOff, maxUnavailable 0 keeps the old pods serving — and because Postgres DDL is transactional and our upgrade is ONE transaction, the failure rolls back completely: the old pods see exactly the schema they know. Review lesson: my indentation and CRLF again — format on save.

### 10.4c-2 Postgres as a StatefulSet
- StatefulSet, not Deployment + PVC: a Deployment's rolling update (maxSurge 1) starts a SECOND Postgres before stopping the first. ReadWriteOnce means one NODE, not one pod: on another node that's a Multi-Attach error, on the same node two postmasters on one data directory (postmaster.pid usually stops it — not something to rely on). A StatefulSet replaces the pod, keeps its name (db-0) and its own disk (volumeClaimTemplates); `persistentVolumeClaimRetentionPolicy: Retain` so `helm uninstall` never deletes the data.
- Facts from the image, not guessed: user `postgres` = uid/gid 1000, set by NAME → runAsNonRoot alone refuses to start ("non-numeric user"), so runAsUser: 1000. fsGroup: 1000 makes a fresh root-owned disk writable; OnRootMismatch skips the recursive chown on every restart.
- readOnlyRootFilesystem for Postgres, tested first with `docker run --read-only`: it needs only data, the socket dir, pg_log and /tmp (+ /dev/shm as a memory volume: 64 MB breaks parallel queries). Git Bash rewrote `/tmp` into a Windows path on the way — MSYS_NO_PATHCONV=1.
- Probes for a database: pg_isready for all three, startup 150 s (initdb on the first start), liveness only after 3 min of silence — restarting a DB mid-recovery makes it worse. And a Kubernetes subtlety: `storageClassName: ""` means "NO class", not "default", so the template omits the field when empty. External DB: `database.host` set → no StatefulSet, every DATABASE_URL points there.

### 10.4c-3 Simulator, seed hook, ingress
- Simulator: 1 replica with `Recreate` — a rolling update would briefly run two and write every reading twice. The price is a few seconds without readings on upgrade: fine for a background producer, unacceptable for the API (RollingUpdate, maxUnavailable 0).
- Seed (plant + knowledge base) as a post-install/post-upgrade hook Job, idempotent, so every upgrade picks up new docs; the 3M-row backfill stays manual. "post-install" means "after Helm CREATED the resources", not "after they're ready": without --wait the API may still be migrating, so the seed has its own migrate init (the advisory lock makes the overlap safe).
- Following that thought found a bug of Claude's: the DB itself may still run initdb when the hook starts. In a Job (restartPolicy Never) each failed init is a failed pod, and backoffLimit 2 (~30 s) dies before initdb is done; the api pod (restartPolicy Always) just retries. backoffLimit 6 covers ~5 min. Same container, different restart semantics.
- Ingress off by default, className traefik for k3s, TLS via cert-manager later; `required` makes "enabled without a host" a render error instead of an Ingress that matches every host. A bad value should fail at `helm template`, not on the cluster.

### 10.4d The chart on a real cluster (Docker Desktop Kubernetes)
- Docker Desktop's `kind` cluster does NOT see local images (a separate containerd in a hidden node): proven with a one-line pod and `imagePullPolicy: Never` → ErrImageNeverPull, before the install could have hung in ImagePullBackOff and looked like a chart bug. kubeadm mode shares Docker's image store. On a server the question disappears: images come from a registry. And Avast's Web Shield intercepts TLS on this machine (the API server's certificate came back as "Avast Untrusted Root") — the same reason git needs schannel here.
- First install deployed at the first attempt: db → api (migrate init 16 s on a fresh DB, startup 7 s vs my 40 s budget) → seed hook after `--wait` (10 machines, 44 docs / 344 chunks). Proved what lint couldn't: $(POSTGRES_PASSWORD) expands from envFrom, fsGroup works on a real PVC. The migrate init also makes the startup probe's worst case rare: the main container only starts right after the DB answered.
- The probe design under real conditions: DB scaled to 0 for 43 hours, the api pod stayed Running with RESTARTS 0 (readiness out, liveness fine) and came back ready by itself; the data survived (PVC). Two corrections of Claude's expectations: EndpointSlices keep not-ready endpoints listed (`ready: false`, kube-proxy skips them), and the first probe failures were timeouts (a terminating pod's IP blackholes packets) before clean 503s — timeoutSeconds 5 made the difference readable.
- Releases: an upgrade with only a config change rolled the api pod (checksum), the seed hook re-ran idempotently; `helm rollback 1` creates revision 3, forward, not back in time. What a rollback does NOT undo: the database schema — so migrations must stay backward-compatible (expand/contract). What uninstall leaves: the PVC (retained on purpose), the Secret (never Helm's), the last hook Job; with reclaim policy Delete, deleting the PVC deletes the data.
